> in any case, retrying if we receive a null response doesn't seem harmful as @twoeths suggested, we should probably have a similar behavior post-gloas

Opened #10479. Post-gloas, a failed getBlobsV2 attempt now arms the same trailing retry as pre-gloas: up to 3 attempts, at least 1 s apart, stopping once the sampled columns are complete.

On devnet data, I looked at `lodestar_data_column_engine_result_total` for glamsterdam-devnet-8 over the last 24h. That's one request per block, about 3.3k per node. The `null` rate depends mostly on the EL:

| EL | null |
|---|---|
| reth | ~1% |
| geth, besu, nimbusel | ~5% |
| erigon | ~16% |
| ethrex | ~30% |
| nethermind | ~61% |

For the same blocks, reth almost always has the blobs while nethermind misses most of them. So the misses look like EL blob pool behavior (for nethermind, likely nethermind#14483), not a question of when in the slot we ask. That isn't enough to pick a slot time for a later retry, which matches your doubt. #10479 doesn't add one. If Hoodi shows `null` answers that later turn into hits, that's the data to revisit it with.
