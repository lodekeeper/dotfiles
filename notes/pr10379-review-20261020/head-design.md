## Current behavior (changed-file observations)

- `packages/builder/src/services/bidder.ts:62–87`: payload attributes supply actual parent beacon root and execution hash. Build identity is `slot:parentBlockRoot:parentBlockHash`; duplicate/in-flight and submitted builds are coalesced. Each distinct build then fetches proposer duties v2 solely for its dependent-root metadata (`:184–189`) and selects preferences by `(proposalSlot, dependentRoot)`.
- The dependent root is NOT the current head block root. It identifies proposer-duty/preference validity for an epoch. Current code correctly names it; do not propose replacing it with `event.block` unconditionally.
- `packages/builder/src/builder.ts:240–255,303–318` subscribes only to block, proposer preferences, payload attributes. `onOpen` already backfills preferences, a natural place for startup/reconnect refresh.
- Bidder captures preferences before awaiting the whole build (`bidder.ts:86–119`) and publishes afterwards (`:147–160`) without canonical-parent / preference-root revalidation. Existing orchestrator has only global lifecycle abort, not per-build cancellation (`payloadOrchestrator.ts:54–69,82–111`). Therefore head tracking that only replaces the duties query does not itself prevent an old in-flight branch build publishing. Treat this as design scope, not a separate full-review finding.

## Existing APIs/patterns (reference only, not PR issues)

- `packages/api/src/beacon/routes/events.ts:99–116,197–209`: legacy `head` exposes block, slot, previous/current duty-dependent roots. **head_v2 already exists here**, with explicit `currentEpochDependentRoot`, `nextEpochDependentRoot`, and `payloadStatus`; its epoch is computed from the **head block slot**.
- `packages/beacon-node/src/chain/chain.ts:1437–1473`: legacy head emitted only on beacon-root changes. head_v2 emitted on root OR payload-status change and maps currentEpochDependentRoot = legacy previousDutyDependentRoot; nextEpochDependentRoot = legacy currentDutyDependentRoot. Same beacon root can change full/empty status; a beacon-root-only tracker cannot observe that via legacy head.
- `packages/api/src/beacon/routes/validator.ts:421–438`: after Fulu proposer duties v2 root for epoch E is canonical block root at `startSlot(E-1)-1` (genesis on underflow). This agrees with the head_v2 current/next mapping, not head block identity.
- `packages/validator/src/services/chainHeaderTracker.ts:45–67,88–107`: VC's small event consumer stores head data and invokes listeners. It has no startup seed / reconnect resync itself; do not oversell it as a complete robustness solution, or import the validator package into builder.
- `packages/validator/src/services/blockDuties.ts:189–233`: post-Gloas VC maps legacy previous root to headEpoch and current root to headEpoch+1, refetching affected cached duties on mismatch. It also has baseline startup/epoch polling (`:128–158`). Useful behavioral pattern, not a reason to share the full service.
- `packages/api/src/beacon/client/events.ts:43,57–72`: onOpen runs on opening; EventSource retries transient errors; onClose is not a generic reconnect signal. 400/500 force close. Recovery work should attach to onOpen. Do not claim event replay or no missed events; none is demonstrated here.
- `packages/beacon-node/src/chain/prepareNextSlot.ts:238–275`: Gloas parent execution hash depends on chosen full/empty variant. Keep parentBlockHash from payload_attributes authoritative for build request, rather than deriving it from beacon root alone.

## Minimal robust recommendation

1. Extend existing builder event subscription/dispatch with a small builder-local latest-head cache; no cross-package abstraction or validator dependency. Prefer head_v2 for Gloas, since already supported at this head and expresses canonical payload status. If legacy head is deliberately chosen for endpoint compatibility, acknowledge it only solves beacon-root / duty-root tracking, not full payload-variant changes.
2. For an event with epoch H = computeEpochAtSlot(event.slot), cache proposer dependent roots under actual epochs H and H+1: v2 currentEpochDependentRoot for H, nextEpochDependentRoot for H+1 (legacy previous/current respectively). Select by **proposalSlot epoch**, including next-epoch proposals built before the boundary. Never blindly use currentDutyDependentRoot for all bids; never call a duty dependent root the head root.
3. Retain an exceptional getProposerDutiesV2 fallback/backfill when no usable event-root cache exists (startup, reconnect, uncovered epoch after long missed slots); refresh on opening/reopening, discard disconnected certainty. Event stream does not promise an immediate head snapshot, and missed slots do not emit a new head merely because the clock epoch advances. The event's epoch is the head block epoch, not wall-clock epoch. Ordinary one-slot boundary crossings are covered by H+1; do not assume every later proposal epoch is. A duties result seeds **only the preference dependent-root cache**, not canonical head identity. Until head identity is known, either seed separately from a REST head snapshot (with race protection) or keep the conservative existing attributes-driven path; don't pretend duties return canonical head.
4. Prevent a slow backfill response overwriting a newer streamed observation (generation guard / apply only if no newer head). Two REST calls for head and duties are not inherently an atomic canonical snapshot. This can stay simple: events are primary, fallback is conditional.
5. Capture branch/preference identity for in-flight work and revalidate before signing/publishing. On canonical-parent or relevant proposer-root change, obsolete jobs must be ignored/canceled and new attributes may start the replacement job. Comparison must include the relevant execution-parent variant if tracking full/empty changes, not merely beacon root. A minimal initial fix is discard stale completion rather than implementing per-job abort; cancellation is an optimization. Avoid blanket invalidation on duplicate/same-state events. A changed duty root does not enumerate every shallow reorg, and a changed beacon root does not necessarily mean a reorg (normal extensions also change it).
6. Keep deadline calculations and fork gating config-driven as current code does. No hardcoded slot timing or pre-Gloas head_v2 subscription promises. This PR currently supports actual bidding only on Gloas (`bidder.ts:80–83`).

## Proposed concise inline reply (root should independently review)

“Agree — I'd keep a small head tracker in the builder and use the roots from the event instead of downloading all proposer duties per build. For Gloas we already have `head_v2`: its `current_epoch_dependent_root` / `next_epoch_dependent_root` map to the head block's epoch / following epoch (the legacy `head` equivalents are `previous_duty_dependent_root` / `current_duty_dependent_root`). That also covers building the first slot of the next epoch; these roots are not the head block root. I'd retain the duties call only as a startup/reconnect or missing-epoch fallback, and recheck the captured parent/preferences before publishing so a build spanning a head change can't publish stale work. `head_v2` also exposes same-block payload-status changes, which legacy `head` doesn't.”

Optional extra if response has room: “Key the roots by the event's head epoch, not the clock epoch: skipped slots may leave the last head in an older epoch.”

## Focused validation cases if implemented

Startup with no new block; reconnect with missed head/reorg; late fallback completion after a new event; ordinary epoch boundary with proposalSlot in next epoch; missed boundary slot; multiple epochs without new block (fallback); reorg while orchestrator waits; duplicate head; same beacon root empty→full (v2); changed parent execution hash under same beacon parent.
